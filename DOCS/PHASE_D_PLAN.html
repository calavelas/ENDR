Phase D — plan

Reframed per the latest decision: Phase D starts on the service page with a file tree + viewer of the service's GitOps files, then layers editing on top.

D1 — Service-page file tree + viewer building

  • New Files tab on the service detail page: repo file tree (left) + syntax-highlighted viewer (right), reusing the create-flow FileTree + CodeBlock components.
  • Shows the files that make up this service: SVCS/<name>/ (README + chart/) for app services; sourcePath folder for platform services.
  • Read-only first. Source of truth = the GitHub repo (so the same surface drives the edit→PR step).

D2 — Edit → PR (the actual FIX) next

  • From the viewer, make a file editable and "Propose change" → opens a services.yaml-only (or values-only) PR; ArgoCD rolls it out → robot comes ONLINE.
  • Reuses the create machinery in ENDR/engine/scaffold/service.py (create_branch + create_or_update_file + create_pull_request); CreateServiceFromPortalRequest already carries env/image — an edit endpoint is a parallel of the create path.
  • Correctness (do up front): developers tune values (overrides.env calibration / values.yaml); the deployment template is platform-owned and must stay read-only. Editing the template teaches the wrong mental model and undercuts the whole pitch.

Pairs with Phase B — robot-validate CI gate next

  • Engine subcommand in reconcile-pr.yml that enforces calibration keys present + values 0–100 and blocks merge otherwise — the visible "policy-as-code guardrail" that validates the FIX PR. Today reconcile-pr.yml only runs services-check, no robot gate.

Open concerns for D1 (file tree + viewer)

  • Data source. GitHub repo (git source of truth; fresh for newly-created services; required for edit→PR) vs the api's local IDP_REPO_ROOT copy (stale for services added after the image build) vs ArgoCD live rendered manifests (rendered, not source — not editable). Recommendation: GitHub.
  • Listing the tree. GitHubClient has get_file_content but no directory listing — needs a new method (GitHub contents/trees API; the api already holds GITHUB_TOKEN). Rate limits → cache per request.
  • Two locations. A service spans SVCS/<name>/ (its chart + README, dev-editable) and the ArgoCD Application manifest under KUBE/ (platform-owned). Show the SVCS/<name>/ folder primarily; the app manifest is read-only context.
  • Editable surface. Only values.yaml / services.yaml overrides should become editable in D2; the chart templates/ render read-only (values-vs-template lesson above).
  • Limits. Text files only; 128 KB content cap (matches the create-flow template-file endpoint).
  • Cluster-free. GitHub-sourced files work even with no cluster — good for the Render demo; degrade gracefully if the repo/API is unreachable.
