ENDR — Robot-demo redesign

Architecture, the IDP↔SDLC journey mapping, and the build plan for the new onboarding experience. This doc is the standing context for that work — read it first.

Companion to DOCS/robot-demo-mockup.html · last updated 2026-06-14

1 · What we're building & why

The default ENDR pitch ("GitOps, ArgoCD, reconciliation") is dry and invisible to non-engineers. The redesign reframes onboarding as an interactive build-a-robot journey: you create a robot service, watch it deploy through a real PR, see it boot broken, fix it, and decommission it — learning the entire GitOps loop by doing it. The robot (a TARS personality) is just the payload; the platform mechanics are the lesson.

One flow, two audiences (narrative toggle)

The same click-through relabels itself for whoever is watching:

  • 🤖 Robot Factory (story mode) — for non-technical people asking "what do you do for your job?"
  • ⚙ Under the hood (IDP) — for people new to GitOps/DevOps and for platform engineers; exposes the real `SVCS.yaml` → TARS → Helm → ArgoCD machinery.

2 · How the real platform works

The mockup is faithful to ENDR's actual GitOps loop. Three surfaces appear in the demo, signalled by the address bar + a coloured tag, because the loop genuinely spans all three:

ENDR portal the self-service UI GitHub source of truth / PR / CI live robot the running service on-cluster

Browser ──▶ ENDR portal (CASE) declare a service │ ▼ opens a PR GitHub: SVCS.yaml ◀── single source of truth │ CI gates the merge (validate-config, robot-validate) ▼ on merge to main TARS (GitHub Action) generates: • app code → SVCS/<name>/app/ (template: endr-robot) • Helm chart → SVCS/<name>/chart/ (template: helm-service) • ArgoCD app → KUBE/clusters/…/services/ │ ▼ reconciles desired → actual ArgoCD deploys to k3d ──▶ <name>.calavelas.net

The two edit layers (the core IDP lesson)

A service has two files that look similar but mean very different things. Understanding the split is the answer to "what does a platform engineer do":

FileOwnerRole
SVCS.yamldeveloper (via portal)The service catalog entry — the high-level "I want a service" abstraction.
chart/values.yamldeveloperThe tunable knobs the platform chose to expose (image tag, port, env, hostnames). Day-2 changes happen here.
chart/templates/deployment.yamlplatform (TARS)The template that renders the knobs into K8s objects. Platform-owned; developers don't touch it.
⚠ Mockup correction (pending): screens s5–s8 currently show the user editing chart/templates/deployment.yaml. That's wrong — personality/calibration edits change the Helm values (chart/values.yaml), and the template renders them. Fixing this turns the edit step into the values-vs-template lesson above. See plan item #1.

3 · The journey, mapped to IDP planes & SDLC

Every screen is one stage of the developer lifecycle. The mockup now carries a persistent stage rail reflecting this — it relabels between factory/IDP wording and highlights the current phase. The full create → break → fix → destroy arc is one complete GitOps loop (plus a day-2 loop-back at the edit step).

The stage rail collapses these into one six-step loop: Declare → Commit → Validate → Deliver → Operate → Retire (factory wording: Design → File spec → Inspect → Assemble → Power on → Decommission). Both create and edit restart the loop at Declare, which is what makes the day-2 loop visible.

4 · The easter egg (keep it)

If a user hand-sets the calibration in the YAML during create (instead of using the form), the robot boots straight to ONLINE and calls them a smart-ass for reading the source. It rewards the engineer who skips the rails — a deliberate signal that the platform doesn't hide its mechanics.

6 · Conversation decisions (context log)

  • Redesign onboarding as an interactive build-a-robot GitOps journey; keep the dual narrative toggle.
  • Two explicit audiences: IDP mode for GitOps/DevOps newcomers + platform engineers; Robot Factory mode to explain the user's job to non-technical people.
  • Edits target Helm values (chart/values.yaml), not the deployment template — and the values/template split is the headline lesson.
  • Next step chosen: build the SDLC/IDP stage rail into the mockup (done) + write this standing doc.
  • Aligns with project constraints: cluster-free/cheap demo path, plain (non-cosmic) naming, clean professional UI — see the demo-strategy & naming notes.
