1 What is ENDR

ENDR is a portfolio-grade "internal developer platform" (think Backstage, Humanitec, or Spotify's golden paths). It demonstrates the full GitOps loop end-to-end.

The promise of an IDP: a developer should be able to stand up a production-shaped service — container build, Helm chart, ArgoCD app, ingress route, a public URL — without knowing Kubernetes. They fill in a short form ("I want a service called cooper"), and the platform does the rest through pull requests and automation, so everything stays auditable in git.

Self-service

A web portal (portal) where you create & browse services and watch them deploy live.

Config-driven

Two YAML files (platform.yaml + services.yaml) fully describe the platform & every service.

Reconciled

The engine renders templates and opens PRs so the repo always matches the desired state.

2 The big idea — desired state, reconciled

Everything flows from one principle: the git repo is the single source of truth. Humans (or the portal) only ever edit the small declarative config; machines generate everything else and keep it in sync.

DESIRED STATE RECONCILE ACTUAL STATE ┌────────────────┐ ┌──────────────────┐ ┌────────────────┐ │ platform.yaml │ │ engine │ │ Kubernetes │ │ services.yaml │ ─────▶ │ renders Helm / │ ─────▶ │ cluster via │ │ (what we want) │ │ ArgoCD manifests│ │ ArgoCD sync │ └────────────────┘ │ → opens PR │ └────────────────┘ ▲ └──────────────────┘ │ │ edit via portal / PR git is truth │ live status └───────────────────────── portal reads back ◀─────────┘
Two reconcile loops stack: the engine reconciles config → generated repo files (via GitHub PRs), and ArgoCD reconciles repo files → live cluster. Neither step is manual.

5 Config = the source of truth

Two root files drive everything. They are deliberately tiny and human-editable; every other file in services/<svc>/chart and KUBE/clusters/.../services is generated from them.

platform.yaml — platform metadata

Who owns the platform, the git coordinates, what clusters/namespaces exist, and the template catalog (the golden paths services can be generated from).

projectName: endr
config:
  git: { provider: github, owner: calavelas, repo: ENDR }
  environments:
    kubernetes: [{ name: mac-lab }]
  namespace: [{ name: demo }, { name: demo2 }]
templates:
  service:  [ python-fastapi, endr-robot ]  # app templates
  gitops:   [ helm-service ]              # chart + ArgoCD app

services.yaml — service catalog

The list of services that should exist. Each entry picks templates, a namespace + environments, and overrides (gateway, pinned image tag, env).

services:
- name: cooper
  namespace: demo
  environments: [ mac-lab ]
  generator:
    service: { template: python-fastapi }
    gitops:  { template: helm-service }
  overrides:
    gateway: { enabled: true }
    image: calavelas/cooper:f04d84a  # ← bumped by CI
Add a service = append ~12 lines to services.yaml. That single edit causes the engine to render a chart + ArgoCD Application, and ArgoCD to deploy it. The image tag is auto-rewritten by CI (<sha>) every time the service's source changes.

6 The golden-path flow (create a service)

What actually happens when a developer creates "cooper" in the portal — the loop the whole project exists to demonstrate.

portal · browser

Fill the form & preview

On /create you pick a name, template, namespace, environment, gateway (advanced: GitOps template). Preview posts dryRun:true → the engine renders into .idp/staging and returns the files that would be generated, plus the new services.yaml.

engine · scaffold/service.py

Open a Pull Request

Submitting posts dryRun:false. It creates a portal/<svc> branch and opens a PR that changes only services.yaml (titled portal - Adding service : cooper). Heavy generation is deferred to CI.

Actions · reconcile-pr.yml

Validate & (optionally) auto-merge

The PR runs engine.py services-check as a read-only drift check. Policy can auto-approve + squash-merge portal PRs that touch only services.yaml, then delete the portal/* branch.

Actions · reconcile.yml

Reconcile on main → generate assets

On merge to main, the engine runs services-check --write-worktree: renders the chart into services/cooper/chart and the ArgoCD app into KUBE/clusters/mac/lab/services/cooper.yaml, and commits them back.

Actions · services-build.yml

Build & publish the image

Changed service source triggers a multi-arch Docker build → Docker Hub. update-image-tags rewrites services.yaml's image: to <sha>, regenerates chart values, commits again.

KUBE · ArgoCD

Sync to the cluster

The services app-of-apps discovers cooper.yaml and ArgoCD syncs the chart into namespace demo: Deployment, Service, HTTPRoute — with CreateNamespace=true.

Gateway · Traefik + Cloudflare

Get a live URL

If gateway.enabled, an HTTPRoute exposes the service at https://cooper.calavelas.net via the Cloudflare tunnel + Traefik gateway.

portal · live

Watch it appear

The create panel polls /api/platform/transactions/<pr#> for pipeline stages, then polls /api/platform until cooper shows up in the catalog with sync/health status. Loop closed.

7 engine — the automation library

One Python package, used two ways: a CLI (ENDR/engine/engine.py) for CI, and imported by the api service for the portal. Shares config/, scaffold/, and templates/.

CLI subcommands (python3 ENDR/engine/engine.py …)

SubcommandWhat it does
services-checkThe reconcile core (was svcs-check). Renders expected assets for every service in services.yaml, diffs against the repo, finds drift + removed services. --write-worktree writes files; --open-pr opens a reconcile PR; --write-scope gitops limits to chart/app files.
discover-changed-servicesMaps a git diff to affected services and emits a GitHub Actions build matrix (context, Dockerfile, image tag).
update-image-tagsRewrites overrides.image in services.yaml to <repo>:<tag> for selected services (preserving formatting via ruamel).

Inside the engine

config/

models.py — Pydantic schema for platform.yaml/services.yaml with k8s-DNS-label validation. loader.py — loads + cross-validates both. paths.py — resolves cluster/app repo paths.

scaffold/

service.py — renders Jinja2 template trees into staging, builds the commit file map, and (non-dry-run) drives branch→commit→PR. github_client.py — thin GitHub REST wrapper.

cli/services_check.py

The reconcile algorithm: render-expected → diff → classify (added/updated/removed) → write worktree and/or open PR → emit JSON + GitHub Actions outputs.

templates/

Golden paths: service/python-fastapi, service/endr-robot (README-only; shared image), and gitops/helm-service (Chart, values, deployment/service/httproute + ArgoCD Application). All .j2.

Key design choice: the portal-created PR only touches services.yaml. Generated files are produced later by the reconcile workflow on main — keeping human-facing PRs tiny and the engine the sole author of generated assets.

9 KUBE — ArgoCD app-of-apps

The cluster is described entirely in git under KUBE/clusters/mac/lab/. ArgoCD bootstraps from one root Application and fans out by sync waves.

core.yaml (root Application, auto-prune + self-heal) └─ core/ ── app-of-apps definitions ├─ platform.yaml (wave 1) ─▶ platform/ argocd · traefik · portal · api · cloudflare ├─ service.yaml (wave 2) ─▶ services/ sample · cooper · finc · miller · test1 └─ gateway.yaml (wave 4) ─▶ gateway/ GatewayClass · Gateways · HTTPRoutes · TLS platforms/ ── vendored Helm charts ├─ argocd/helm (self-manages, Redis-HA subchart) └─ traefik/helm (ingress + Gateway API CRDs)

platform

Cluster-wide services: ArgoCD itself, Traefik, the portal & api apps (platform/portal.yaml, platform/api.yaml), and the Cloudflare tunnel.

services

One ArgoCD Application per app service, each pointing at services/<name>/chart. Discovered via directory.recurse.

gateway

Gateway-API resources + Cloudflare tunnel routes exposing services at *.calavelas.net (the portal at portal.calavelas.net + endr.calavelas.net).

Every app runs auto-prune + self-heal with CreateNamespace=true, so the cluster continuously converges to whatever the repo says — the second reconcile loop.

11 api — the platform snapshot model

The read-side (formerly the cosmic "PLEX universe", now de-themed). build_platform_snapshot() assembles a PlatformSnapshot the portal renders: platformServices + services, each a ServiceNode with sync/health, image tag, source path.

Two data sources, graceful fallback

ModeWhenStatus values
dataSource:"argocd"API_ARGOCD_SERVER set & reachable — hits ArgoCD's /api/v1/applicationslive Synced / Healthy, real image tags & deploy times
dataSource:"config"no ArgoCD creds, or the API call failsa snapshot derived purely from services.yaml + manifests, with a warning

It re-reads the remote services.yaml from GitHub (raw.githubusercontent.com) so the portal reflects the true source of truth. This is why the demo at endr.calavelas.net works even without cluster credentials.

Env knobs: API_ARGOCD_SERVER / API_ARGOCD_TOKEN / API_ARGOCD_VERIFY_TLS (live data) · API_SERVICES_CONFIG_URL (which services.yaml to read) · API_SERVICE_GATEWAY_DOMAIN (defaults calavelas.net). The portal reads ENDR_API_URL + PORTAL_* (embed/github) env.

13 Robot lifecycle in progress

The "build-a-robot" demo (DOCS/robot-demo-mockup.html) is being wired in as a real service lifecycle: create → break → fix → destroy, all via GitOps. Full plan in DOCS/ROBOT_LIFECYCLE_PLAN.html.

A robot is just a normal ENDR service whose behaviour is 100% env-driven, running the shared calavelas/endr-robot image (apps/robot/app.py): set HUMOR/HONESTY/TRUST (sum>0) and it boots ONLINE; leave them empty and it boots MALFUNCTION. Calibration lives in services.yaml overrides.env, so both create and fix are services.yaml-only PRs.

A · endr-robot service template — registered in platform.yaml; renders chart + ArgoCD app with calibration env in the deploymentdone
C · portal create with personality — ROBOT_NAME/CATCHPHRASE/HUMOR/HONESTY/TRUST fields when the robot template is selectednext
D · portal values-edit flow — PR a robot's calibration env (the "fix")todo
B · robot-validate CI — required check: calibration keys present + values 0–100todo
