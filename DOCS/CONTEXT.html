ENDR

A GitOps Internal Developer Platform (IDP). Developers click a button to create a new service; the platform writes config to GitHub, an automation engine generates all the Kubernetes manifests, and ArgoCD deploys it to a cluster — no kubectl, no copy-paste.
GitHub = source of truth Next.js portal FastAPI + Python engine ArgoCD app-of-apps Helm + Jinja2 templates k3d / local k8s Demo: endr.calavelas.net

1 What is ENDR

ENDR is a portfolio-grade clone of the "internal developer platform" idea (think Backstage, Humanitec, or Spotify's Backstage golden paths) — the running joke baked into the UI is "Damn… I should have used Backstage." It is built to demonstrate the full GitOps loop end-to-end.

The promise of an IDP: a developer should be able to stand up a production-shaped service — container build, Helm chart, ArgoCD app, ingress route, a public URL — without knowing Kubernetes. They fill in a short form ("I want a service called cooper"), and the platform does the rest through pull requests and automation, so everything stays auditable in git.

Self-service

A web portal (CASE) where you create & browse services and watch them deploy live.

Config-driven

Two YAML files (ENDR.yaml + SVCS.yaml) fully describe the platform & every service.

Reconciled

An engine (TARS) renders templates and opens PRs so the repo always matches the desired state.

2 The big idea — desired state, reconciled

Everything flows from one principle: the git repo is the single source of truth. Humans (or the portal) only ever edit the small declarative config; machines generate everything else and keep it in sync.

DESIRED STATE RECONCILE ACTUAL STATE ┌───────────────┐ ┌──────────────────┐ ┌────────────────┐ │ ENDR.yaml │ │ TARS engine │ │ Kubernetes │ │ SVCS.yaml │ ──────▶ │ renders Helm / │ ──────▶ │ cluster via │ │ (what we want)│ │ ArgoCD manifests│ │ ArgoCD sync │ └───────────────┘ │ → opens PR │ └────────────────┘ ▲ └──────────────────┘ │ │ edit via portal / PR git is truth │ live status └────────────────────────── CASE portal reads back ◀─────┘
Two reconcile loops stack on top of each other: TARS reconciles config → generated repo files (via GitHub PRs), and ArgoCD reconciles repo files → live cluster. Neither step is manual.

5 Config = the source of truth

Two root files drive everything. They are deliberately tiny and human-editable; every other file in SVCS/<svc>/chart and KUBE/clusters/.../services is generated from them.

ENDR.yaml — platform metadata

Who owns the platform, the git coordinates, what clusters/namespaces exist, and the template catalog (the "golden paths" services can be generated from).

projectName: endr
config:
  git: { provider: github, owner: calavelas, repo: ENDR }
  environments:
    kubernetes: [{ name: mac-lab }]
  namespace: [{ name: demo }, { name: demo2 }]
templates:
  service:  [ python-fastapi ]   # app code template
  gitops:   [ helm-service ]      # chart + ArgoCD app

SVCS.yaml — service catalog

The list of services that should exist. Each entry picks templates, a namespace + environments, and overrides (gateway on/off, the pinned image tag).

services:
- name: cooper
  namespace: demo
  environments: [ mac-lab ]
  generator:
    service: { template: python-fastapi }
    gitops:  { template: helm-service }
  overrides:
    gateway: { enabled: true }
    image: calavelas/cooper:f04d84a  # ← bumped by CI
Add a service = append ~12 lines to SVCS.yaml. That single edit causes TARS to render a Dockerfile, a Helm chart, and an ArgoCD Application, and ArgoCD to deploy it. The image tag is auto-rewritten by CI (git-<sha>) every time the service's source changes.

6 The golden-path flow (create a service)

What actually happens when a developer creates "cooper" in the portal. This is the loop the whole project exists to demonstrate.

CASE · browser

Fill the form & preview

On /create you pick a name, templates, namespace, environment, gateway. Clicking preview posts dryRun:true → TARS renders into .idp/staging and returns the exact files that would be generated, plus the new SVCS.yaml.

TARS · scaffold/service.py

Open a Pull Request

Submitting posts dryRun:false. TARS creates a case/<svc>-<ts> branch and opens a PR that changes only SVCS.yaml (titled CASE - Adding service : cooper). The heavy generation is deferred to CI.

GitHub Actions · tars-pr.yml

Validate & (optionally) auto-merge

The PR runs TARS.py svcs-check as a read-only drift check. A policy can auto-approve + squash-merge CASE PRs that touch only SVCS.yaml, then delete the case/* branch.

GitHub Actions · tars-build.yml

Reconcile on main → generate assets

On merge to main, TARS runs svcs-check --write-worktree: it renders the full Helm chart into SVCS/cooper/chart and the ArgoCD app into KUBE/clusters/mac/lab/services/cooper.yaml, updates the README service table, and commits them back.

GitHub Actions · svcs-build.yml

Build & publish the image

Changed service source triggers a multi-arch Docker build → pushed to Docker Hub. update-image-tags rewrites SVCS.yaml's image: to git-<sha>, then regenerates the chart values and commits again.

KUBE · ArgoCD

Sync to the cluster

The services app-of-apps discovers cooper.yaml and ArgoCD syncs the Helm chart into namespace demo: Deployment, Service, HTTPRoute — with CreateNamespace=true.

Gateway · Traefik + Cloudflare

Get a live URL

If gateway.enabled, an HTTPRoute exposes the service at https://cooper.calavelas.net via the Cloudflare tunnel + Traefik gateway.

CASE · live

Watch it appear

The create panel polls /api/plex/transactions/<pr#> for pipeline stages, then polls /api/plex until cooper shows up in the catalog with sync/health status. Loop closed.

7 TARS — the automation engine

One Python module, two entrypoints: a CLI (ENDR/TARS/TARS.py) used by CI, and a FastAPI app (TARS/api/main.py) used by the portal. Both share config/, scaffold/, and templates/.

CLI subcommands (python3 ENDR/TARS/TARS.py …)

SubcommandWhat it does
svcs-checkThe reconcile core. Renders expected assets for every service in SVCS.yaml, diffs against the repo, finds drift + removed services. --write-worktree writes the files; --open-pr opens a reconcile PR; --write-scope gitops limits to chart/app files. Also rewrites the README service table.
discover-changed-servicesUsed by CI: maps a git diff to affected services and emits a GitHub Actions build matrix (context, Dockerfile, image tag) for Docker Hub or GHCR.
update-image-tagsRewrites overrides.image in SVCS.yaml to <repo>:<tag> for selected services (preserving formatting via ruamel). This is how a new build SHA propagates into desired state.

Inside the engine

config/

models.py — Pydantic schema for ENDR.yaml/SVCS.yaml with k8s-DNS-label validation. loader.py — loads + cross-validates both. paths.py — resolves cluster/app repo paths.

scaffold/

service.py — renders the Jinja2 template trees into a staging dir, builds the commit file map, and (non-dry-run) drives branch→commit→PR. github_client.py — thin GitHub REST wrapper.

cli/svcs_check.py

The reconcile algorithm: render-expected → diff → classify (added/updated/removed) → write worktree and/or open PR → emit JSON summary + GitHub Actions outputs.

templates/

Golden paths: service/python-fastapi (app, Dockerfile, requirements) and gitops/helm-service (Chart, values, deployment/service/httproute + ArgoCD Application). All .j2.

Key design choice: the CASE-created PR only touches SVCS.yaml. All the generated files are produced later by the TARS workflow on main. This keeps human-facing PRs tiny and makes the engine the sole author of generated assets — no drift from hand-edits.

8 CI/CD — the GitHub Actions workflows

Four workflows in .github/workflows/ implement the automation. They are the muscle behind the golden-path flow above.

WorkflowTriggerDoes
tars-pr.ymlPR touching ENDR.yaml/SVCS.yamlRead-only svcs-check drift check; optional auto-approve+merge policy for CASE service PRs; cleans up merged case/* branches.
tars-build.ymlPush to main (config changed)Reconcile → svcs-check --write-worktree to render manifests → commit "TARS : Sync generated assets" → trigger the service image build.
svcs-build.ymlService source change / dispatchdiscover-changed-services → multi-arch Docker build → push to Docker Hub → update-image-tags + regenerate chart values → commit "Persist image tag".
endr-build.ymlENDR/CASE/** or ENDR/PLEX/** changeBuilds the case + plex platform images. PRs validate build only; main pushes images and bumps CASE/chart & PLEX/chart values.yaml with the new <sha7> tag.
Secrets/vars used: DOCKERHUB_USERNAME / DOCKERHUB_PASSWORD for image publish, GITHUB_TOKEN for PRs, and repo var TARS_DELETE_SOURCE_BRANCH_ON_MERGE to toggle branch cleanup. You can see this rhythm directly in the git log: feat(idp): register service … → TARS : Sync generated assets → TARS : Persist image tag ….

9 KUBE — ArgoCD app-of-apps

The cluster is described entirely in git under KUBE/clusters/mac/lab/. ArgoCD bootstraps from one root Application and fans out by sync waves.

core.yaml (root Application, auto-prune + self-heal) └─ core/ ── app-of-apps definitions ├─ platform.yaml (wave 1) ─▶ platform/ argocd · traefik · case · plex · cloudflare ├─ service.yaml (wave 2) ─▶ services/ sample · cooper · miller · test1 (directory.recurse) └─ gateway.yaml (wave 4) ─▶ gateway/ GatewayClass · Gateways · HTTPRoutes · TLS platforms/ ── vendored Helm charts ├─ argocd/helm (wave −2, self-manages, Redis-HA subchart) └─ traefik/helm (wave 0, ingress + Gateway API CRDs)

platform

Cluster-wide services: ArgoCD itself, Traefik ingress, the CASE & PLEX platform apps, and the Cloudflare tunnel.

services

One ArgoCD Application per app service, each pointing at SVCS/<name>/chart. Discovered automatically via directory.recurse.

gateway

Kubernetes Gateway-API resources + Cloudflare tunnel routes that expose services at *.calavelas.net. Uses ServerSideApply.

Every app runs with auto-prune + self-heal and CreateNamespace=true, so the cluster continuously converges to whatever the repo says — that's the second reconcile loop.

11 PLEX — the "universe" model

PLEX is the read-side. It assembles a PlexUniverse the portal renders: a galaxy of coreApps (platform) and services, each a PlexNode with sync/health, image tag, source path, and an orbitBand (a space-themed ring index).

Two data sources, graceful fallback

ModeWhenStatus values
dataSource:"argocd"PLEX_ARGOCD_SERVER set & reachable — hits ArgoCD's /api/v1/applicationslive Synced / Healthy, real image tags & deploy times
dataSource:"config"no ArgoCD creds, or the API call fails"Unknown" — a snapshot derived purely from SVCS.yaml + manifests, with a warning

It even re-reads the remote SVCS.yaml from GitHub (raw.githubusercontent.com) so the portal reflects the true source of truth, and it cross-checks ArgoCD's services app to avoid showing stale/pruned services. This is why the demo at endr.calavelas.net works even without cluster credentials.

Env knobs: PLEX_ARGOCD_SERVER / PLEX_ARGOCD_TOKEN / PLEX_ARGOCD_VERIFY_TLS (live data) · PLEX_SVCS_CONFIG_URL (which SVCS.yaml to read) · PLEX_SERVICE_GATEWAY_DOMAIN (defaults calavelas.net, builds the per-service URL).
