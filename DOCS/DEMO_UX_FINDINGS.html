Demo UX Findings

A cold, first-time-user evaluation of the live ENDR platform (endr.calavelas.net). Independent evaluators drove the running site with no prior knowledge of how ENDR works and no access to the source — exactly like a first-time visitor — then reported every point of friction.
3 personas live site, real services 3 eval rounds create → live → decommission

1 Method

Each evaluator was given only a persona and the public URL — no architecture, no code — and had to complete a full round trip by following only what the site itself showed (its UI, hints, and the TARS/CASE assistant). They drove a real browser and created/decommissioned real services.

Layperson

A non-technical person in Interstellar mode. Has never heard of servers, Git, Kubernetes, or "deployments."

DevOps engineer

Senior platform engineer in IDP mode. Knows GitOps / K8s / ArgoCD cold; judges critically and verifies against GitHub.

Junior developer

Codes and knows the SDLC (PRs, CI, review) but has never done ops — Helm/ArgoCD/clusters are foreign.

2 Headline

It's real, not mocked. The DevOps evaluator independently verified the full chain via gh: create → PR → CI gate → auto-merge → reconcile (chart + ArgoCD app committed) → image build → decommission PR. The architecture page and the robot's claims checked out. Friction clustered almost entirely in the "what happens after I click Create" window.

By the final round, all three personas completed the full lifecycle (create → provisioning → live → decommission), including the non-technical layperson and the no-ops junior developer.

4 Spotlight — orphaned workloads on decommission

The sharpest infra bug. ArgoCD only cascade-deletes an app's resources if the Application object carries the finalizer resources-finalizer.argocd.argoproj.io. The child apps didn't (verified live: finalizers: None), so when the services app-of-apps pruned a child Application on decommission, the object was removed but its Deployment/Service/route were orphaned and kept running indefinitely — not just lagging.

One-time cleanup. Services decommissioned before the finalizer fix have no Application left, so the finalizer can't reach them — their orphaned workloads need a manual delete: 
kubectl delete deployment,service,httproute <name> -n <namespace> --ignore-not-found
Fixed going forward. The child-app template now sets the finalizer, so every future decommission cascade-deletes the workload. Combined with the ArgoCD auto-refresh (below), decommission is now hands-off and prompt.

6 Fixes shipped

  • Concurrency — .gitattributes sets services.yaml merge=union so simultaneous creates keep both entries; auto-merge also updates a behind branch before merging.
  • Decommission cascade — child ArgoCD apps now carry the cascade-delete finalizer.
  • No ~3-min wait — after reconcile pushes manifests, CI hard-refreshes the services app-of-apps via the ArgoCD API (the "Refresh" button, automated); config-edit refreshes the edited app.
  • Never a hard 404 — the service route shows a friendly auto-refreshing state across the whole window: being created → provisioning → live; neutral copy for removed/unknown.
  • Correct slug — the chart injects SERVICE_NAME, so the robot's ENDR link and self-decommission always use the real service name.
  • Smoother guidance — the robot says the PR auto-merges itself and the service appears on the dashboard; a "where is it?" reassurance sets expectations; decommission is described as automatic.
  • Delivery list — dropped the stale pipeline badge + per-PR polling; the PR link is the CI source of truth.
  • Assistant layout — bottom sheet below 1024px so it no longer covers the create form.

7 What worked well (keep)

  • Genuinely end-to-end and verifiable — real PRs, real CI gates, real ArgoCD artifacts.
  • Create wizard — 4 steps, live two-way Form⇄YAML, and a Review step showing the full file diff before committing.
  • Under-the-hood page — coherent, accurate, honest about guardrails.
  • The Interstellar toggle — a real emotional hook for non-technical visitors.
  • TARS/CASE — the chat actually taught the junior dev GitOps, anchored on Git/PR concepts.

8 Still open (roadmap)

Lower-priority polish: plainer language on the default IDP landing; guidance on the namespace field; broaden the assistant's chip set (or label it a guided tour, not free-form chat); reproduce the "Add variable" form-reset report. Larger IDP gaps a real team would want: rollback UX, secrets management, multi-environment promotion, real RBAC/SSO, observability depth, more templates.
